## Part 1 — What was done: the Rules → Scenes rename

### Why
The integration is being framed as a **condition-based scene engine**. The concept previously called a "rule" is better understood by users as a **scene** (a named outcome like "Movie night" that carries its own conditions and actions). "Rule" put the plumbing in front of the user; "scene" puts the thing they actually want in front. This rename retires the word "rule" from both the UI and the code.

The decision history (terminology debate, why "scene", why not "rule-based") is captured in user memory `ambience-rules-to-scenes-rename.md`.

### What changed
A full, deterministic rename of `rule`/`Rule` → `scene`/`Scene` (case-sensitive substring replace; plurals fall out automatically) across:
- **Backend** (`custom_components/ambience/**/*.py`): `Scene`/`SceneEval` types, `scene_enabled`, the per-scope **`scenes`** storage key and wire key, WS command **`ambience/scene/run_actions`**, `scene_index` / `scene_name` payload fields, helper functions (`reassign_orphan_scenes`, etc.).
- **Frontend** (`frontend/src/**/*.ts`): the `Scene` type; files renamed `rule.ts → scene.ts`, `views/rule-editor.ts → views/scene-editor.ts`, `views/rules-list.ts → views/scenes-list.ts`; custom elements `ambience-scene-editor` / `ambience-scenes-list`; all `*-scene` events (`add-scene`, `delete-scene`, `reorder-scenes`, `edit-scene`, `run-scene-actions`, `duplicate-scene`, `toggle-scene-enabled`, `unpin-scene`, `cancel-scene`, `save-scene`); CSS classes; API functions; the bundle was rebuilt.
- **Tests**: `tests/**/*.py` and `test/**/*.ts` (incl. file renames `test_run_rule_actions.py → test_run_scene_actions.py`, `rule-editor.test.ts → scene-editor.test.ts`, `rules-list.test.ts → scenes-list.test.ts`).

### The rename script (re-runnable)
A deterministic script was used. **Re-run it if/when the in-flight test-suite branch lands and brings new files that still say "rule"** (then rebuild the bundle and run the checks above). Save this somewhere durable — it lived in `/tmp` which is ephemeral:

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(git rev-parse --show-toplevel)"
count=0
while IFS= read -r f; do
  LC_ALL=C sed -i '' -e 's/Rule/Scene/g' -e 's/rule/scene/g' "$f"
  count=$((count + 1))
done < <(
  git ls-files \
    '*.py' '*.ts' \
    'custom_components/ambience/strings.json' \
    'custom_components/ambience/translations/en.json' \
    'custom_components/ambience/services.yaml' \
    'README.md' \
  | grep -v '^custom_components/ambience/frontend/.*\.js$'
)
echo "Rewrote $count files."
```
After running: `npm install` (if Biome is missing), `npm run build`, `python -m scripts.gen_reference_docs --write`, `npm run format`, then the gates via `make lint-py lint-js translations docs-check coverage-py coverage-js build-check`. Two known prose artifacts recur each time the sed runs on fresh code and were fixed by hand: the docstring in `service_logbook.py` (`Names the matched scene ("scene")` → drop the redundant `("scene")`) and the CSS comment in `scenes-list.ts` (`this scene carries layout` → `this CSS rule carries layout`, because there "rule" means CSS rule).

## Part 2 — Brief for writing the documentation

The original task was to **completely rewrite the user docs with mkdocs**. It was deferred behind this rename and is **not started**. Everything below is the agreed plan.

### Audience & voice
- Reader is **familiar with Home Assistant but is not a programmer**.
- **No jargon**, or define a term before first use.
- **British English** (e.g. "colour", "behaviour", "organise").
- **Humble and straightforward** — do not sell or justify the product; just explain it.
- Write in **full sentences, like a human**. Give simple examples.
- **Avoid "it's not X, it's Y" constructions.** Avoid frequent em-dashes.

### Terminology to use (this is the whole point of the rename)
- Ambience is a **condition-based scene engine** for Home Assistant. (Not "rule-based"; not "conditional".)
- A **scene** = a named outcome (e.g. "Movie night") with three parts: a **name**, the **conditions** that call for it (the "when"), and the **actions** it runs (the "then").
- Other first-class nouns, unchanged: **scopes** (House / Floor / Area), **conditions**, **actions**, **categories**.
- One-liner to anchor the intro:
  > Ambience is a condition-based scene engine for Home Assistant. You describe scenes for each room and give each one the conditions that should bring it about. Ambience watches your home and applies the best-matching scene automatically.
- **Clarify once**, where relevant: Home Assistant has its own built-in **Scenes** (saved snapshots of entity states). Ambience scenes are a different thing (they are conditional). Mention this briefly so users do not conflate them.
- The service name `ambience.apply_scene` now reads correctly: "apply the matching scene".

### Documentation decisions already made (with the user)
- **Scope:** the **full doc set** — getting started + a concepts guide + a complete reference for every condition type and every setting.
- **Automations:** only **mention** the per-scope switch entities where relevant. **Do not** write a dedicated `apply_scene` / automations page for this first release.

### Suggested page structure (starting point, adjust as needed)

2. **Installation** — HACS custom repository + manual; restart; add the integration. (See current `README.md`.)

5. **Conditions reference** — one section per condition (details below).
6. **Actions & exposed actions** — what an action is, the Settings → Actions list, visible fields vs always-sent defaults, the re-apply interval.
7. **Settings reference** — switch defaults, categories, per-condition setup (time-of-day periods, day workday source, weather entity + groups).
8. **Tips / testing** — the Traces viewer (why a scene won) and the Simulator ("what if") tool.

### Authoritative system model (verified from code — use this, do not guess)

**Resolution / precedence** (`engine.py`):
- Scenes are evaluated in order, top to bottom. A scene matches when **all** its conditions pass; an absent or `null` condition is a wildcard (always passes). **First matching scene wins**; evaluation stops there.
- A **disabled** scene (`enabled: false`) is skipped entirely — never wins, never short-circuits the scenes below it.
- A scene that can never win (something above it always matches first) is shown as **"Never fires — shadowed by an earlier scene."**
- **Categories** partition a scope's scenes; each category is resolved independently, so a scope can have one winning scene per category at the same time.

**Scopes & switches** (`switch.py`):
- Scopes: **House** (one), each **Floor**, each **Area** (Areas come from HA's own area registry).
- Each scope has one `switch.*_ambience` entity. Turning a switch **on or off cascades down** to descendant switches; there is **no upward cascade** (turning an Area off does not affect its Floor or the House).
- A scope's switch **gates that scope's scenes**: when off, automatic applies are skipped. Manual "Run actions" in the panel forces a run regardless (`force=True`).
- **Auto-on delay**: when a switch is turned off, a timer starts; when it fires the switch turns back on. Default **7200s (2h)**; **0 disables** auto-on. Global default + per-scope override (Settings → Ambience).

**Service** (`services.yaml`, `service.py`): `ambience.apply_scene` (admin-only) resolves a scope's scenes and runs the winning scene's actions per category.

**The eight condition types** (`custom_components/ambience/conditions/*.py`; user labels in `strings.json`). For each, document what it checks and how it is configured:

| Condition | Checks | User configures |
|---|---|---|
| **Time of day** | Current time, absolute or sun-relative | Named period (built-ins: Morning, Afternoon, Evening, Nighttime, Daytime; plus custom) **or** one or more time ranges whose endpoints are a clock time (hh:mm) or a sun anchor (dawn/sunrise/noon/sunset/dusk/midnight) with an optional ± minute offset |
| **Entity state** | A boolean expression over entity states | A tree of conditions (is / is not / >, >=, <, <= on a state or attribute), combined with AND / OR / NOT, with an optional "for" duration |
| **Sun** | The sun's angular position | Elevation min/max (degrees, −90..90) and/or azimuth as 8-point compass sectors (N, NE, …) or custom circular ranges; at least one required |
| **Weather** | Weather state and numbers | A weather entity, condition groups (built-ins Sunny / Dim / Dark / Wet / Windy, plus custom groups), and numeric thresholds on temperature / apparent temperature / humidity / wind speed / pressure |
| **People** | Who is (not) at home or in a zone | Quantifier (anyone / everyone / nobody), location (home or a named zone), optional negate, optional "for" duration; optionally limited to specific people |
| **Day** | Date / weekday / workday | Include/exclude items: day of week, day of month, date (annual), date range, last day of month, workday, holiday, first/last workday of month. Workday/holiday need a configured workday sensor or calendar (Settings → Conditions) |
| **Template** | A Jinja template → true/false | A Jinja template string; rendered against current state, coerced to a boolean the way HA does |
| **Script** | A HA script returning `{match: bool}` | A script entity, optional arguments, and an optional list of entities to re-evaluate on (the script is opaque to the engine) |

**Exposed actions** (`exposed_actions.py`, Settings → Actions): a reusable action template. For each, the user picks a HA service, chooses which fields are **visible** in the scene editor, sets **defaults** that are always sent (fields can be hidden-but-always-sent, the old "locked" behaviour), and an optional **re-apply interval** (re-run the action every N seconds while the scene stays matched; a scene's action can override per use).

**Panel surfaces to describe** (`frontend/src/`): the main scopes view (collapsible House/Floors/Areas, each with its switch, scene list, category filter, add-scene), the scene editor modal (name, category, When = conditions, Actions), the Settings modal (Ambience / Conditions / Actions tabs), the Traces viewer (why a scene won, per-condition results) and the Simulator ("what if" tool).
